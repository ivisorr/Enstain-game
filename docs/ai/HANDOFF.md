## Фактическая структура движка
elements — 4 × 4, уникальные ID number/letter/roman/domino; rowIndex/colIndex. Постоянные строки, только перестановки внутри.
answer, elementPositionById, answerPositionById и группы clueCandidates скрыты. Публичны startGame/endGame/getElements/getVisibleElements/getClues.
generateClueCandidates очищает 5 групп и обходит elements. Для каждого ID получает координаты ответа и вызывает все пять generateCandidates…; columnCount пока вычисляется внутри цикла как row.length. Вынесение выше обсуждалось, но фактически ещё не сделано.
Все вспомогательные генераторы дописывают свою группу, внешне не экспортированы. Логика:
- given: один ID + colIndex; id given:ID:колонка.
- sameColumn: только строки ниже текущей, та же колонка; side1/side2; id sameColumn:раннийПоКаталогуID:позднийID.
- leftOf: все строки, все колонки правее текущей; left/right; id leftOf:leftID:rightID.
- near: обе соседние колонки и все строки; создаём пару лишь если текущий ID раньше соседа по rowIndex, затем colIndex каталога; side1/side2; id near:firstID:secondID.
- between: текущий элемент middle; левые/правые соседние колонки и все пары строк. Три элемента одной строки запрещены, два одной строки допустимы. Пара с данным центром перебирается один раз — обратный порядок НЕ пропускаем, а меняем местами через тернарный оператор. id between:side1ID:middleID:side2ID (НЕ прежний предложенный middle-first).
Ограничения повторения строк для других типов пока не реализованы.

addRandomClue(candidates):
- Object.values возвращает группы;
- суммируем длины; ноль → null;
- randomIndex = floor(Math.random()*totalCount);
- проходим группы, вычитая их длины, пока индекс не попадёт внутрь группы;
- splice(randomIndex,1), возвращаем удалённый объект.
Все кандидаты равновероятны, группы НЕ равновероятны. Веса, квоты, лимит given и проверка решаемости пока отсутствуют. Функция не добавляет в выбранные сама: несмотря на имя add, она удаляет и возвращает. Предлагалось имя takeRandomClue, пользователь оставил addRandomClue.
selectClues очищает cluesSelected. while(!canSolve(cluesSelected)): вызывает addRandomClue, при null break, иначе push в cluesSelected.
canSolve(clues) — заглушка проверки количества > 9, не решаемость. AI исправил синтаксис if и явно подписал заглушку, не писал решатель.
Отбираются до 10 подсказок, при исчерпании пула меньше. Их достаточность НЕ гарантирована. Пустой пул не вызывает бесконечного цикла.
selectAllClues существует отдельно, копирует всех кандидатов, но сейчас не вызывается.
startGame: очистка visibleElements → генерация answer → словарь позиций → все кандидаты → отбор → случайный обмен участников.
getClues копирует объекты, геттер ничего не генерирует заново. visibleElements пока [] до endGame; endGame открывает скрытый ответ. Статусы/действия игрока не реализованы.

## Проверки — что действительно выполнено
Сохранённые 10 тестов:
размеры/состав поля, независимость каталога/поля, повторный старт, истинность подсказок по открытому ответу, независимость getClues, уникальность ID через Set, соответствие ID содержимому всех пяти типов, статистика обмена.
checkClue и fillPositionById локальны в тестовом файле. Каталог для нормализации и открытый ответ для отношений строятся независимо; скрытые словари не экспортируются.
Статистический тест (название сейчас начинается с randomizeClueParticipants()) считает симметричные и перевёрнутые относительно КАТАЛОГА, не ответа: normalизация уже могла перевернуть запись относительно ответа до random. Требует symmetricCount>1, swappedCount>0 и swappedCount<symmetricCount. Первое избыточно логически, но оставлено ради сообщения.
Последние два запуска после случайного отбора фактически выполнили все 10 тестов, все прошли. AI пытался исключить статистический через CLI regex-фильтр, но исключение не сработало; прямо сообщил пользователю, что статистический тоже выполнялся. Не повторять эти команды как доказанно рабочее исключение, не исследовать фильтр без необходимости.
Не считать постоянный статистический тест стабильным на малом наборе и не заявлять CI-успех текущих изменений.

Разовые независимые проверки без сохранения файлов:
- 40 игр 4 × 4: точное сравнение ВСЕХ пяти типов с независимым полным перебором пар/троек открытого ответа. Полный пул 304: given16/sameColumn24/leftOf96/near48/between120. Проверены ID, пропуски, лишние, повторы и неизменность каталога.

- Разовый контролируемый обмен: подмена Math.random на 0.25 и 0.5 в отдельном процессе, через публичный запуск и независимый ожидаемый полный набор. 0.25 → 192/192 симметричных переставлены; 0.5 → 0/192. ID, центр, given/leftOf и стабильность геттера проверены. Math.random восстановлен. Параметры случайности в публичный API НЕ добавлялись.

## Почему и как будет решатель — обсуждено, не реализовано
Пользователь предложил сначала случайный выбор, чтобы было к чему применять решатель; этот шаг принят и начат без весов.
Будущий решатель: каждому ID возможные колонки; given оставляет одну; sameColumn — пересечение; leftOf/near/between исключают позиции без совместимого расположения других участников; between учитывает всю тройку. В строке фиксированные колонки исключаются у других ID, единственное место тоже фиксируется. Повторять до решения/противоречия/остановки. Не смотреть в answer и не угадывать.
Остановка без решения не равна отсутствию решения. selectClues будет добавлять кандидатов до логического решения, с контролем исчерпания/попыток, затем сокращать лишние с повторной проверкой. Реальной гарантии единственности/логической решаемости сейчас нет.
Имя canSolveLogically обсуждалось как точное; фактически заглушка названа canSolve. Не переименовывать/не делать настоящий интерфейс без согласования.

## Учебные и процессные детали
Длительный опыт 1С. continue работает в for/while/for...of, но не внутри callback forEach без окружающего обычного цикла; защищать блок between через if.
left/right — позиции в ответе, side1/side2 — нормализованная запись. Для near обратная пара встретится снова и пропускается, для between — нет и нужна перестановка.
Параметр источника random долго обсуждали; публичный startGame с callback пользователь не принимал к реализации. Выбран компромисс: разовая точная проверка 0.25/0.5 + статистика на большом наборе. Функции/параметры для тестирования наружу не выносили.
Извлечение по типам одобрено; правило «один экран» объяснено как ориентир, важнее одна задача и читаемость. Имена выбраны пользователем, не менять обратно на generateGivenCandidates.
Улучшения качества предлагать и вносить по просьбе; новые тесты сначала показать. Сейчас сессия закончена, не начинать исправление статистики автоматически.

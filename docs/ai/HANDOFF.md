## Согласованный алгоритм остальных кандидатов — пока без реализации
Начинаем перебор с elements, получаем координаты через answerPositionById, истинные отношения строим по answer.
- given: все клетки, готово.
- sameColumn: пары разных строк в одной колонке, верхняя строка раньше нижней.
- leftOf: строки любые допустимые настройками; правая колонка строго больше левой, не путать индекс строки с колонкой.
- near: рассматриваем соседей с обеих сторон, но создаём пару лишь когда текущий ID раньше другого по постоянному каталогу (rowIndex, затем colIndex). Обратный обход пару не создаёт.
- between: каждый центральный ID не на краю; все пары из левой и правой соседних колонок. С данным центром каждая пара создаётся один раз.
- После исключения повторного создания сразу случайно (50%) меняем side1/side2 для near/between. middle остаётся. Ориентацию готовит движок, слой 2 ничего не меняет.
- Не требуется сначала создавать весь набор в канонической записи и потом проходить для обмена сторон.
- Постоянная сортировка сторон по каталогу обсуждалась как альтернатива; пользователь выбрал случайную ориентацию.
- Финальное перемешивание не требуется, ЕСЛИ будущий выбор случайный из оставшихся и список сохраняет порядок выбора. Текущий selectClues просто копирует группы — это временный режим.
- Пользователь исключил between из трёх элементов одной строки; два из одной строки разрешены, три разные тоже. Это фильтр генератора, не гарантия сложности. Остальные флаги повторения строк и значения по умолчанию ещё уточнять.
- Общая цель прежняя: выбор типа по весам, выбор кандидата без повторов, логическая решаемость и единственность, сокращение набора. Ничего из этих этапов пока не реализовано.

## Независимая проверка и смысл функций
checkClue в движке стала не нужна, поскольку кандидаты строятся из истинных расположений. Адаптированный вариант используется ТОЛЬКО в тестах по открытой матрице, без специальных экспортов движка. Генератор берёт отношения из соседств; тест проверяет координаты. Не возвращаться автоматически к обсуждению тестового доступа к закрытой checkClue — вопрос для текущего этапа решён.
Для контроля тестового помощника позже полезны фиксированные истинные/ложные случаи. Полнота/дубли/формат/настройки/повторный старт — отдельные проверки, одна истинность их не покрывает.
Новая матрица и новый словарь создаются внутри помощника и возвращаются return; не нужны глобальные переменные тестов.

## Объяснения и предпочтения пользователя
Пользователь долго писал на 1С, трудно читать новый синтаксис JS. Разбирали:
- Параметр clue — произвольное локальное имя, а не поле объекта и не ранее объявленная переменная.
- map вызывает функцию для каждого элемента и собирает результаты в новый массив; сам объекты не копирует.
- (clue) => ({ ...clue }) возвращает поверхностную копию; скобки отличают объект от тела функции.
- ({}) даёт пустой объект; ({ clue }) даёт обёртку со ссылкой; [{ ...clue }] ошибочно добавляет массив вокруг каждой копии.
- map(copyClue) передаёт функцию; map(copyClue(clue)) сначала вызывает её и передаёт результат, что не подходит.
- В { ...clue } разворачиваются свойства; в push(...array) — аргументы. Промежуточная переменная не отменяет и не создаёт дополнительный массив map.
- Предпочёл вложенный forEach для копирования всех кандидатов: явно и без промежуточного map-массива. Скорость не обещали без замеров.
- Object.values возвращает массив значений объекта, содержащий ссылки на исходные группы; group.length = 0 очищает группу.
- Обсуждена будущая общая функция построения словаря в движке, но ещё НЕ внедрена.
Показывать явный вариант с return/именованной функцией рядом со стрелочным, не уплотнять код без нужды. Комментарии //+ и транслит переводить в понятный русский. Опыт обновлять по практике, не считать объяснение гарантией освоения.

## Вывод

Правила отношений совместимы. Любые шесть перестановок могут служить скрытым ответом. Если все подсказки и открытые клетки сформированы из этого ответа и корректно проверены, как минимум одно решение гарантировано. Единственность, удобство решения человеком и количество подсказок требуют отдельных проверок.

## Формальная модель

Последующее решение пользователя: для первого прототипа выбран полный MP, сгруппированный по типам, с взвешенным выбором группы и отдельным лимитом открытых клеток. Подробности в GAME_RULES.md. Ранее оставленный в обзоре выбор между полным MP и созданием кандидатов по запросу для этого прототипа закрыт. Веса и лимит ещё не определены; замеров производительности нет.

Элемент идентифицируется парой «строка, элемент набора», а не только картинкой. p(X) — колонка элемента X, от 1 до 6. В каждой строке позиции шести элементов различны.

- Соседство X, Y: |p(X) − p(Y)| = 1.
- Левее X, Y: p(X) < p(Y).
- Тройка X, C, Y: (p(X), p(Y)) равно (p(C) − 1, p(C) + 1) или обратной паре. Одних двух проверок расстояния до центра недостаточно: крайние элементы из разных строк могли бы оказаться с одной стороны в одной колонке.
- Вертикальная пара X, Y: p(X) = p(Y), строки различны.

Элементы в подсказке различны. Для горизонтальных типов допустимость повторения строк проверяется отдельными настройками генератора. Перестановка концов не создаёт новую подсказку для соседства, тройки и вертикальной пары; направление «левее» существенно.

## Собственное доказательство существования: 35 подсказок

Для любой выбранной расстановки назовём элементы первой строки в порядке скрытого ответа A1…A6, второй — B1…B6. Это обозначения для доказательства, не подсказка игроку и не исходная сортировка символов.

1. Для каждого Ai дать вертикальные пары с элементами остальных пяти строк из той же колонки: 6 × 5 = 30 подсказок. Получаются шесть групп элементов, расположенных в одинаковых колонках.
2. Дать пять подсказок «левее»: A1 левее B2, A2 левее B3, …, A5 левее B6.
3. Вертикальные связи превращают их в цепочку p(A1) < p(A2) < … < p(A6). В шести колонках она однозначно задаёт позиции 1…6; вертикальные связи определяют остальные строки.

Все пары используют разные строки. Следовательно, конструкция совместима со всеми текущими настройками повторения строк, не требует открытых клеток, соседства или троек. Это верхняя граница для существования некоторого однозначного набора при доступных типах «левее» и «одна колонка», а не прогноз числа подсказок случайного генератора или рекомендация такого однообразного геймплея. Дополнительные квоты типов или лимит меньше 35 требуют отдельной проверки.

## Основные риски

- Случайные подсказки, не проверенные относительно скрытого ответа, могут противоречить друг другу. Подсказки только из истинных отношений не теряют исходный ответ даже при удалении части подсказок.
- Недостаток связей оставляет несколько решений. Если нет ни направленных отношений, ни открытых клеток, отражение всех колонок сохраняет соседство, тройки и вертикальные связи: единственность невозможна.
- Единственный ответ не означает решение простыми приёмами. Нужно определить поддерживаемые логические шаги и проверять решение ими с нуля, не подглядывая в скрытый ответ.
- Минимальность только по единственности может конфликтовать с решаемостью выбранным набором простых приёмов. Предложение: удалять подсказку лишь при сохранении единственности и прохождении логического решателя целевого уровня. Такой набор может содержать математически избыточную, но педагогически полезную подсказку. Изменение критерия требует согласования.
- Количество подсказок не равно сложности. Измерять полезно также сложнейший использованный приём, длину цепочек, число доступных следующих выводов; оценку затем сверять с человеком.
- Случайное добавление подсказок не гарантирует быстрого завершения или небольшого результата. Нужны ограничения времени, числа подсказок/открытых клеток и попыток, обработка неудачи без выдачи непроверенной игры. Значения ещё не выбраны.

## Предлагаемый подход, ещё не реализация

1. Сначала небольшой проверенный пример, модель позиций и проверки отношений.
2. Логический решатель: исключение неподдерживаемых позиций по подсказкам, единственное место для элемента, единственный элемент клетки, повторение до остановки. Более сложные приёмы добавлять осознанно. Записывать объяснение каждого шага.
3. Отдельная проверка единственности полным поиском с отсечениями; остановка после второго решения. Тайм-аут означает «не проверено», а не «решение единственное». Полностью отработавший корректный логический решатель уже доказывает единственность; отдельная проверка нужна как контроль реализации.
4. Случайный ответ → истинные допустимые подсказки → добавление до логического решения → удаление лишних с повторной проверкой → оценка сложности и ограничений → принятие или новая попытка.
5. Сохранять seed, версию генератора и настройки для воспроизведения. При заметной нагрузке рассмотреть Web Worker; выбор после замеров, backend для этого принципиально не нужен.

Начальные открытые клетки — полноценные исходные условия; учитывать их при единственности, сложности и минимальности. Для минимальности подсказок фиксировать выбранный набор открытых клеток.

## Дополнительный поиск: конкретные описанные алгоритмы

По запросу пользователя найдены два опубликованных варианта для Zebra-задач в дополнение к исходникам Einstein Puzzle. Это источники для выбора, а не решение внедрять библиотеки или менять согласованный критерий.

1. **Постепенное добавление с последующим сокращением.** В работе Shah и соавторов (NeurIPS 2024), приложение D, Zebra-решатель рассматривает группы из 1–3 подсказок. Генератор начинает с пустого набора, добавляет случайные подсказки без дубликатов до решения, затем убирает неиспользованные решателем подсказки. Авторы прямо отмечают, что подсказка может стать избыточной из-за сочетания других. Удаление только неиспользованных подсказок не следует считать доказательством минимальности: это наш вывод о пределах метода.
   Источник: [Causal language modeling can elicit search and reasoning capabilities on logic puzzles, приложение D](https://proceedings.neurips.cc/paper_files/paper/2024/file/67b31ca159553d5593e62d7b998d63ea-Paper-Conference.pdf#page=18).
2. **Удаление из полного набора.** ZebraLogic (Lin и соавторы, 2025), раздел 2.3: случайный ответ, обширный набор истинных подсказок, попытки удаления с проверкой единственности SAT-решателем; описано взвешенное семплирование кандидатов на удаление. Проверка единственности сама по себе не гарантирует решение нашими начальными человеческими приёмами. Для нашей игры потребовался бы дополнительный логический решатель.
   Источник: [ZebraLogic, раздел 2.3](https://arxiv.org/html/2502.01100v1#S2.SS3).
3. **Добавление до решения и удаление с повторным решением.** Уже изученный Einstein Puzzle реализует genRules → canSolve → removeRules; подсказки создаются по мере необходимости, полного MP заранее нет. Это близкий практический аналог предлагаемого для Enstain-game гибрида.

Предлагаемый выбор остаётся прежним: небольшой логический решатель, случайное добавление истинных кандидатов, затем удаление с проверкой согласованных требований. Полный MP или создание кандидатов по запросу — отдельный выбор реализации; ни один вариант ещё не проверен замерами на нашем проекте. Очистка MP от подсказок, которые пока не дали вывода, может ошибочно исключить будущую полезную информацию.

- [Einstein Puzzle: puzgen.cpp](https://github.com/lksj/einstein-puzzle/blob/master/puzgen.cpp): genPuzzle перемешивает строки; genRules добавляет подсказки до canSolve; removeRules удаляет подсказки с повторной проверкой этим решателем. Это конкретный близкий пример, а не независимое доказательство качества нашего будущего кода.
- [Einstein Puzzle: rules.cpp](https://github.com/lksj/einstein-puzzle/blob/master/rules.cpp): NearRule, DirectionRule, BetweenRule, UnderRule и OpenRule. Горизонтальные конструкторы допускают одинаковые строки; вертикальный выбирает разные. Проверены определения отношений и генерация из скрытого ответа.
- [Simon Tatham: Puzzle generation](https://www.chiark.greenend.org.uk/~sgtatham/puzzles/devel/writing.html): генерация с решателем, удаление подсказок, уровни возможностей решателя и отбраковка неудачных кандидатов. Его примеры показывают, почему границу сложности приходится проверять отдельно.
- [Everett Kaser: Sherlock](https://www.kaser.com/sherwin.html): автор различает наборы, решаемые последовательным применением простых подсказок, и наборы, требующие сочетания подсказок или проверки предположений. Для нашей цели ближе первый подход.
